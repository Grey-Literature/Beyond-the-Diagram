Back to the Remote Access / VPN trailhead

Not every VPN appliance uses RADIUS. Plenty authenticate straight against AD over LDAP instead — a genuinely different wrinkle, with its own severe failure class that individual password troubleshooting can't touch at all.

Simple bind vs. search-then-bind

A simple bind authenticates directly with the user's own credentials. Search-then-bind first logs in as a dedicated service account to search the directory for the user's DN, then binds as that user — which means the appliance's own service account is now a second, independent point of failure that has nothing to do with any end user's password.

The severe failure class: the whole auth path is dead

This is categorically different from any individual user's credentials being wrong:

  • The appliance can't reach a domain controller at all
  • A DC's LDAPS certificate quietly expired — a silent, calendar-driven failure with zero connection to any user's password activity
  • In search-then-bind setups, the appliance's own service account is expired, disabled, or locked
The tell is scope: if every user fails at once, in the same way, testing individual passwords is a waste of time before you've even started. That's the signature of the whole path being down, not any one credential.

The diagnostic sequence that actually works

  1. Substitute a known-good account through the identical path first — if it also fails, the problem is upstream of any individual credential, full stop.
  2. Check the appliance's dedicated auth/debug log, not its connection/session log — the session log only knows a connection happened and ended, not why.
  3. Run ldapsearch from a neutral host using the same service account, to test directory health independent of whatever the appliance chooses to report.

A real vendor pattern worth knowing by name

Barracuda firewalls have a documented failure mode: an MSAD reboot can cause the firewall's own auth service to time out — and not self-recover. It needs a manual service restart even after AD comes back healthy. The general shape: a service holding persistent state to an upstream dependency that doesn't detect the bounce and reconnect gracefully on its own — the same shape as DCLocator caching a dead DC from the AD/GPO module, just on the appliance side of the fence instead of the client side.

A forward-looking note

Windows Server 2025 defaults LDAP server signing requirements to Require Signing (2019/2022/2016 defaulted to negotiable). That specifically breaks appliances doing a simple, unsigned bind over plain LDAP:389 — it doesn't force full LDAPS, just signed LDAP or LDAPS with channel binding. Worth confirming vendor support before any DC upgrade.
