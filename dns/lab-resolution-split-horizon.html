Two things worth watching directly: how a name actually gets resolved (and why the answer can be stale), and what it means for the same hostname to have two legitimately different correct answers depending on who's asking.

1. The resolution chain

A client doesn't usually talk to an authoritative server directly — it asks a recursive resolver to do the walking:

client → recursive resolver → root → TLD (.com) → authoritative server for the domain

Every step's answer gets cached for as long as its TTL says, by every resolver along the way — including ones you don't control, like a user's ISP or a corporate proxy. That's why a DNS change can be "done" on your end and still not visible to someone else for minutes or days: you changed the source, not every cached copy of the old answer.

2. Split-horizon (split-brain) DNS

Plenty of organizations intentionally run two views of the same zone: an internal resolver that returns a private IP for app.example.com, and a public one that returns something else (or nothing) for the exact same name. That's normal and deliberate — the failure mode is the two views drifting out of sync when only one of them gets updated.

Compare the two views directly rather than guessing which one is "right":

nslookup app.example.com <internal-dns-ip>
nslookup app.example.com 8.8.8.8
If these disagree, that's not automatically a bug — confirm first whether split-horizon is intentional for this name before treating the public answer as broken. The actual bug is usually that one view got updated and the other didn't.

3. Registrar / nameserver cutover

Moving a domain to a new DNS provider is the sharpest version of the TTL problem: the propagation window is governed entirely by every resolver's cached TTL out in the world — nothing you do makes it faster. Worse, any record that isn't explicitly recreated at the new provider — MX, SPF, DKIM, random verification TXT records nobody remembers exist — just silently stops resolving, with no error to point at.

Mitigation is boring but effective: pull a full zone export from the old provider before cutover, so there's a complete list to reconcile against instead of discovering missing records one broken integration at a time.
