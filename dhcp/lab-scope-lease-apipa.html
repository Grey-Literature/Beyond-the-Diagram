Back to the DHCP trailhead

Three things to actually watch happen, in order: configuring a scope, a lease going through its full renewal cycle, and what a client does when no offer comes back at all. The goal isn't memorizing the commands — it's building the mental model that makes the Case and Drill for this module make sense.

1. Configure a scope

A scope is just a range the server is allowed to hand out, plus the options that go with it:

Add-DhcpServerv4Scope `
  -Name "VLAN20-Clients" `
  -StartRange 10.20.0.100 -EndRange 10.20.0.200 `
  -SubnetMask 255.255.255.0 -State Active

Default lease duration is 8 days unless you set it otherwise. That number matters more than it looks like it should — it's the clock everything in the next section runs on.

2. Watch a lease actually happen, then expire

A successful lease is a four-message exchange, always in this order:

DHCPDISCOVER  (client, broadcast)  →
DHCPOFFER     (server, unicast)    →
DHCPREQUEST   (client, broadcast — yes, still broadcast, even though it now knows the server)  →
DHCPACK       (server, unicast)

Once a client has a lease, check it from the server side:

Get-DhcpServerv4Lease -ScopeId 10.20.0.0

The lease doesn't just sit there until it dies — the client tries to renew it twice, on a schedule set by the lease duration:

  • T1 (50% of the lease) — client sends a unicast DHCPREQUEST straight back to the server that issued the lease. Quiet, one-to-one, usually invisible unless you're capturing traffic.
  • T2 (87.5% of the lease) — if T1 got no answer, the client gives up on that specific server and broadcasts instead, asking any DHCP server to renew it (rebinding).
  • Lease expiry — if T2 also gets nothing, the client drops the address entirely. It doesn't fall back to the old one "just in case."
This is why a saturated pool can look completely healthy for days: renewal traffic is unicast and low-volume, so a pool that's technically full can keep serving existing clients right up until something needs a brand-new lease and there's nothing left to give it. Get-DhcpServerv4ScopeStatistics is how you'd actually catch that before it bites.

3. Watch APIPA kick in when nothing comes back

If a client's DHCPDISCOVER gets zero offers — server down, relay broken upstream, pool exhausted, doesn't matter which — Windows clients self-assign a 169.254.x.x address after a short timeout, rather than sitting with no address at all. That's Automatic Private IP Addressing (APIPA).

The important part: a 169 address doesn't tell you why nothing came back, only that nothing did. The client never got past step one of the exchange above. That's genuinely useful information — it rules out anything that would require the exchange to have completed — but it's the start of an investigation, not the end of one.

The only way to see this directly is on the wire: filter a capture on bootp || dhcp and look for a DHCPDISCOVER with no reply at all within the retry window.
