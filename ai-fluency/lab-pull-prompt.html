Lab: The pull-prompt

This is the Description leg: how to describe the work so you get useful behavior back. It assumes you've already decided an assistant is the right tool for this — that call comes first — and it doesn't yet cover judging what comes back, which is its own leg. Everything here sits in the research step of the troubleshooting loop: you have a complaint, you don't yet have a hypothesis, and this is how you get from one to the other.

The failure mode this fixes is specific. A tech in a high-uncertainty state — vague symptom, no idea where to start — pastes the symptom into an AI and gets back one of two things: a single confident-sounding guess they implement without testing, or a generic list of possibilities with no way to check any of them.

Both waste time. The second one is arguably worse, because it looks helpful. A well-organized list of five plausible causes feels like progress right up until you realize you're no closer to knowing which one it is than before you asked.

The same problem, asked two ways

Here's a real-shaped scenario: Monday morning, users at one branch office can't reach the file server. It worked Friday. Nobody reports changing anything.

The push prompt — asking for an answer

You
users at our branch office can't access the file server this morning, worked fine friday, what's wrong?
AI

This is most commonly a DNS resolution issue — after a weekend of DHCP lease renewals, clients often pick up a stale or incorrect DNS server and can no longer resolve the file server's hostname. Here's what to look at:

  1. DNS resolution — verify clients can resolve the file server's FQDN.
  2. SMB service state — confirm the Server service is running and listening on 445.
  3. Firewall rules — check whether anything is blocking SMB between the branch subnet and the server.
  4. Share and NTFS permissions — confirm the affected users still have access rights.
  5. Network path — verify routing between the branch and the site hosting the file server.
  6. Authentication — check for expired passwords or a broken secure channel on the clients.

Start with DNS, as that's the most likely culprit given the symptoms.

Be honest about this answer: it isn't stupid. Every item on that list is a real thing that really causes this. It's well-organized, it's fast, and it sounds like it was written by someone who's done this before. That's exactly the problem — it's confident enough to steer you. An unsure tech reads "start with DNS" and spends the next twenty minutes on DNS. And notice what the list doesn't contain: a single instruction for how to check any of the six items, or any way to tell which one you're actually looking at. It narrowed nothing. It restated the search space and put a confident guess on top.

The pull-prompt — asking to be interviewed

You
I'm troubleshooting an IT issue and I want you to interview me, not answer me. Symptom: users at one branch office can't reach a file server this morning. It worked Friday. No known changes. My scope: I'm a tier-2 tech with domain admin, RMM agents on all endpoints and servers, read access to the firewall, and remote console to the switches. There is nobody physically on site today. Don't propose a fix yet. Ask me ONE diagnostic question at a time, chosen to eliminate as much of the possibility space as it can. For each question, tell me exactly how to check the answer — the specific command, log, or tool — because I may not already know how to test it. Also tell me what each possible answer would rule out.
AI

Question 1: Is this affecting every user at that branch, or only some of them?

How to check: Don't poll users — that's slow and their reports are unreliable. Use your RMM to run Test-NetConnection <fileserver> -Port 445 on three or four endpoints at that site, including at least one machine nobody has reported a problem on. If you can, run the same test from a machine at a different site as a control.

What the answers rule out: If every branch endpoint fails and the control site succeeds, this is site-scoped — network path, routing, or firewall — and we can drop per-user permissions, passwords, and anything client-specific entirely. If only some branch machines fail, it's not the path, and we look at what those machines have in common. If the control site fails too, the branch is a red herring and the server itself is the problem.

Tell me what you get and I'll pick the next split from there.

Same model, same scenario, roughly the same amount of typing. The difference isn't the AI's intelligence — it's what you asked it to do. One question, chosen to cut the space roughly in half, with a concrete way to answer it and a stated consequence for each outcome. That's half-splitting, applied to a conversation instead of a wire.

The part techs actually get wrong

It isn't enough for the AI to ask a good narrowing question. "Is this one user or everyone?" is a genuinely good split — and completely useless to someone who doesn't know how to establish that. Faced with an unpaired question, a tech under pressure will do one of three things: guess, answer from impression ("I think it's everyone?"), or go ask users and take their word for it. All three feed bad data into the next split, and every question after that inherits the error.

The actual skill is noticing when a question arrives without a check attached, and asking for the pairing out loud rather than answering anyway. One sentence does it: "How would I check that? I have RMM, firewall read access, and no one on site."

The knowledge of where that evidence lives is what the rest of this platform's domain modules are for. That's why AI fluency can't be a standalone module — it's the thing that makes the other modules usable in the moment you need them.

A third shape: the discovery prompt

Push and pull aren't the whole set. There's a third mode that gets used constantly without having a name, and naming it matters because reaching for the wrong one of these three is a specific, recognizable failure.

Push You have enough context and you know what you want. Ask directly. Appropriate far more often than this Lab's opening example implies — the failure isn't pushing, it's pushing when you couldn't have described the problem properly in the first place.

And be honest inside it. If you know there are holes in what you're handing over — you don't have that log, you can't reach that box, you genuinely don't know how to check that piece — say so in the prompt. An unflagged gap gets quietly filled with an assumption you'll never see. A flagged one usually gets addressed, and naming it is often what turns a push prompt into a partial discovery request without you having to start over. "I don't know how to get that" is useful information, not an admission.
Pull You can't articulate the answer, but you know roughly what the space of causes looks like. Ask it to interview you, one question at a time, and narrow toward a cause.
Discovery You don't yet know what evidence even exists. Ask it to walk you through what could be looked at — which logs, on which box, what tests to run, what to ask the client — before narrowing anything at all.

Pull and discovery feel similar and do opposite things. Pull narrows toward a cause. Discovery widens the evidence surface. Using pull when you needed discovery is how you end up narrowing confidently inside a space that never contained the answer — every question good, every answer honest, and the actual cause was in a log nobody mentioned.

The diagnostic signal: a push prompt that gets no traction is telling you something about your prompt, not about the model. It means there wasn't enough information in it. Re-rolling the same push prompt with different wording is the reflex, and it doesn't work — the fix is to switch modes. If you can name the possible causes, go to pull. If you can't even do that, go to discovery.

All three live in the research step of the troubleshooting loop, which is worth knowing because everything downstream — hypotheses, experiments, conclusions — inherits whatever this step got wrong.

The rest of the pattern

  • Feed it evidence incrementally. The loop only works if you report back what you actually found after each check. Otherwise it keeps reasoning from your increasingly stale opening description instead of from real data.
  • State scope and capability up front — your role, your access level, your tooling (RMM, packet capture, admin rights, remote-hands-only). Skip this and it burns turns suggesting things you can't do, or worse, assumes an access level you don't have and hands you a plan that dead-ends three steps in. Blind spots belong in the same declaration: what you don't have, and what you wouldn't know how to go get.
  • Paste verbatim, never paraphrase. "It says something about a trust issue" is already lossy — you've thrown away the distinction between "the trust relationship failed" and "the domain is not available" before the AI ever saw it. Same "learn to read what's actually printed" discipline that applies to reading an error yourself, applied to what you feed in.
  • Treat its hypothesis like a search result, never a verdict. An AI can produce a confident, well-written, wrong answer with exactly the shape of a forum post that matches your symptom but not your cause. Verify against the live system before you act on it — that's the entire point of the Case in this module.
  • Know when the loop isn't worth it. Production is down, you need hands on keyboard now, and you have two strong candidates — just check them. A multi-turn interview costs more than it saves under acute pressure. This pattern earns its keep in the "lots of unknowns, no idea where to start" state it was designed for, and nowhere else.

Now run both yourself

Reading a comparison isn't the exercise. The responses above are worked examples — yours will differ, and the differences are the interesting part. Take a symptom you're currently stuck on, or the last one that took you too long, and run it twice through whatever AI tool you actually use.

One caveat if you're doing this somewhere unfamiliar — a blind model arena is a good place to watch prompt shape change output, and a bad place to paste a live ticket, because you can't know which company received it. Invent the topology and the hostnames if so; the lesson transfers even when the data was never real. See Diligence for where that line sits.

First, the push version. Type the symptom the way you'd normally type it:

<your symptom, one or two sentences, the way you'd normally ask>

Then, in a fresh conversation, the pull version:

I'm troubleshooting an IT issue and I want you to interview me, not answer me.

Symptom: <symptom, verbatim error text if you have one>

My scope: <your role, access level, and available tooling — RMM, packet
capture, admin rights, remote hands, whatever you actually have>

Don't propose a fix yet. Ask me ONE diagnostic question at a time, chosen
to eliminate as much of the possibility space as it can. For each question,
tell me exactly how to check the answer — the specific command, log, or
tool — because I may not already know how to test it. Also tell me what
each possible answer would rule out.

Then compare, and specifically check these:

  • Did the push version lead with a confident single cause? Would you have chased it?
  • Did the pull version's first question actually split the space, or just ask for detail?
  • Did every question come with a real check attached — a command, a log path, a tool — or did any arrive unpaired? When one does, demand the pairing and note what you get back.
  • Run the pull loop for three or four turns, feeding back real results. Did it narrow, or did it start recycling the same suggestions? Recycling usually means you stopped giving it new evidence.
