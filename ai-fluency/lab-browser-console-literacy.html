Lab: Reading a browser console

This is a genuinely distinct literacy gap for a lot of ITOps people, and it's not a character flaw — most of us were never taught how a web page actually works. If you live in IP addresses, DNS records, and directory objects, a console log looks like noise from someone else's job.

The cost of that isn't just missed information. It's misclassification in both directions: dismissing something as "an app problem, not mine" when it's your infrastructure, or escalating "the network is broken" when it's application code. Both burn a day and some credibility.

The 60-second model of what's happening

A page isn't one thing arriving. The browser fetches an HTML document, then reads it and fetches everything it references — scripts, stylesheets, images, fonts — each as its own separate request, potentially to entirely different hosts. Once running, the page's JavaScript makes further requests of its own in the background to APIs.

Two consequences worth internalizing:

  • "The page loaded" doesn't mean everything worked. The document can arrive perfectly while a dozen sub-requests fail. That's why a page can look subtly broken with no error message anywhere — the errors are in the console, and nowhere else.
  • One page can span several hosts and several trust boundaries. "The site is down" from a user might mean one background API call to a different domain is failing while everything else is fine.

Open it with F12 (or Ctrl+Shift+I / Cmd+Option+I) and look at two tabs: Console for errors the page raised, Network for what was actually requested and what came back. Network is usually the more useful of the two for infrastructure work — it shows status codes, timing, and the real response headers.

Four errors worth recognizing on sight

Could be yours

CORS: "blocked by CORS policy"

Access to fetch at 'https://api.internal.example.com/v1/status' from origin
'https://portal.internal.example.com' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Usually a backend header misconfiguration — genuinely the dev team's. But an SSL-inspecting corporate proxy that decrypts, rewrites, and re-signs responses can strip or mangle that header on the way through. Then it's your infrastructure producing an error that reads as application code. Recognizing "this might be my proxy, not their app" is the valuable move, and the reason this one can't be reflexively forwarded.

Cheapest disambiguation: request the endpoint from inside the inspected path and from outside it, and compare the raw response headers.

Usually the dev team's

Mixed content

Mixed Content: The page at 'https://portal.example.com/' was loaded over HTTPS,
but requested an insecure resource 'http://portal.example.com/js/legacy.js'.
This request has been blocked; the content must be served over HTTPS.

An HTTP resource referenced from an HTTPS page. Almost always leftover from an incomplete HTTPS migration — a hardcoded http:// URL somebody missed. The browser blocks it silently, so the page just looks subtly broken with no visible error unless the console is open. Worth knowing precisely because there's nothing to see from the outside.

Squarely yours

net::ERR_CONNECTION_REFUSED / "Failed to fetch"

GET https://api.internal.example.com/v1/status
net::ERR_CONNECTION_REFUSED

This is an actual connectivity failure — nothing answered, or something actively refused. DNS, routing, firewall, or a service that isn't listening. This is the one entry on this list that reliably means "go network-troubleshoot," where the others mostly don't.

It's also the useful contrast for the CORS error above: a CORS message proves the response arrived — the browser read it and objected to a header. If nothing had arrived, you'd be looking at this error instead.

Could be yours

Certificate warnings

GET https://intranet.example.com/
net::ERR_CERT_AUTHORITY_INVALID

Expired cert, incomplete chain, hostname mismatch — or an inspecting device re-signing the connection with a CA the client doesn't trust. The error text alone doesn't distinguish them, and the most common cause is not always the actual one. Read the certificate the affected client actually received, not the one you see from your own desk. The Case in this module is built entirely around that distinction.

Classify before you diagnose

Same move as the authn/authz module, applied to a domain ITOps traditionally never gets taught at all. Before reacting to console output, sort it:

1. Mine to fix. Connectivity, DNS, certificates, proxy behavior, firewall.
2. Escalate to the dev team. Application logic, backend headers, an incomplete migration in their code.
3. My infrastructure wearing a web-shaped disguise. The dangerous bucket — it reads as bucket 2 and belongs in bucket 1. Inspecting proxies are the usual culprit.

Bucket 3 is why this is a classification exercise and not a lookup table. The reflex — "console error, therefore app team" — is right often enough to feel reliable, which is exactly what makes it expensive the times it isn't.

Where AI helps here, and where it doesn't. Pasting a verbatim console error and asking what it's asserting is a legitimately good use — it's a translation task, and they're good at translation. Asking "whose problem is this?" is not, because that answer depends on your topology: whether you run an SSL-inspecting proxy, whether that user is behind it, what your migration state is. Supply that context or expect the statistically-common answer, which is bucket 2 every time.

Try it

Open the console on an internal web app you support — one that works fine — and just read what's already there. Most production sites have several errors and warnings sitting in the console at all times.

  1. Sort each one into the three buckets above.
  2. For each, write one sentence on how you'd confirm your classification rather than assume it.
  3. Paste one you can't classify, verbatim, into an AI — and ask what the error is asserting, not who's at fault.

Doing this on a working app is deliberate: you learn what normal console noise looks like, which is the only way to recognize abnormal later.
