## Phase 5 — AI Fluency module (done)

Built as `ai-fluency/`, following the same per-domain-folder shape as the nine domain modules but deliberately labelled a **meta-skill module** rather than given an ordinal — it's the one module whose techniques are all gated on knowing where the evidence lives, which is what the other nine are for. Three Labs instead of one, because the concept doc names three distinct sub-skills and says two of them are legitimate Lab/Drill content in their own right.

- [x] The pull-prompt pattern (`lab-pull-prompt.html`) — the core failure mode, then a **side-by-side push-prompt vs. pull-prompt comparison with both responses written out in full**, then the question+verification pairing discipline, then the five supporting habits (feed evidence incrementally, state scope/capability up front, paste verbatim, hypothesis-not-verdict, know when the loop isn't worth it), then a "now run both yourself" exercise with both prompts in copyable blocks and four specific things to compare. No live model call, no API key, no backend — exactly as Phase 1 predicted it wouldn't need.
- [x] The weak response is written to be **genuinely tempting, not a strawman** — a well-organized, plausible six-item list with a confident "start with DNS" lead. The lab says so out loud ("be honest about this answer: it isn't stupid") and then names precisely what's wrong with it: it narrowed nothing and paired no item with a way to check it. A weak example that's obviously bad teaches nothing, since nobody is fooled by the version they'd recognize.
- [x] Anti-easter-egging Case (`case-ai-near-miss.html`, island `case-ai-near-miss`) — a certificate warning at one branch, with the AI's confident diagnosis (expired cert / missing intermediate, plus a coherent explanation for why it looks site-scoped) presented up front as a quoted artifact. Correct root cause is an SSL-inspecting firewall re-signing the connection with a CA that branch's machines don't trust. Three moves rather than the usual good/risky pair: implementing the AI's answer, reading the cert the *affected client* actually received (the only move that can distinguish the three causes), and checking the cert from your own desk — the last being **right instinct, wrong vantage point**, which is a more useful wrong answer than an obviously careless one.
- [x] Drill: unpaired narrowing question (`drill-unpaired-question.html`, island `drill-unpaired-question`) — a verbatim AI reply that is a genuinely *good* half-split and still needs pushing back on, because no verification method came with it. Links to the diagnostic-methodology page.
- [x] Packet capture literacy (`lab-packet-capture-with-ai.html`) — the mechanical point (binary file, `tshark` extraction, and the filter step *being* half-splitting one layer earlier than usual) and then the harder conceptual one, **baseline articulation**: an anomaly is a comparison, so the AI can't find one until you state what should have happened. Explicitly framed as the AI-fluency and protocol-mechanism modules meeting in the middle, with the baseline example sourced straight from the DHCP Lab. Includes the Signal-vs-Silence catch that in a filtered capture, absence is ambiguous *by construction* unless you say what you filtered.
- [x] Browser console literacy (`lab-browser-console-literacy.html`) — a 60-second model of how a page actually loads (since the gap is real and not a character flaw), the four errors worth recognizing on sight (CORS, mixed content, `ERR_CONNECTION_REFUSED`, cert warnings), and the three-bucket classification: mine / the dev team's / **my infrastructure wearing a web-shaped disguise**. Names where AI helps here (translating a verbatim error) and where it can't (whose problem it is — that depends on topology it doesn't have).
- [x] Drill: CORS classification (`drill-console-cors.html`, island `drill-console-cors`) — correct answer is "can't tell yet from this line alone," since the reflex forward-to-the-dev-team is right often enough to be expensive when it isn't. The "network is down" distractor gets its own rebuttal from the error itself: a CORS message *proves the response arrived*, which is Signal vs. Silence in a place ITOps rarely thinks to apply it.

### Phase 5b — the other three Ds

The first pass covered **Description** only (pull vs. push, product/process/performance specification, minimum viable context) and stopped there. Tasha's own course notes — the Anthropic AI Fluency framework worked through against nine years of real MSP incidents — carry the other three competencies, and several of them turn out to connect to machinery this platform already has rather than sitting alongside it. Module reorganized around all four legs plus the three interaction modes.

- [x] **Delegation** (`lab-delegation.html`) — Problem Awareness including the reframe that *"no idea, let's poke and find out"* is the **advanced** form of it rather than a failure (that's the state every Case here drops you into on purpose); Platform Awareness as matching tool to task shape, including knowing when the tool is your monitoring rather than a model; the judgment line that doesn't move; and the tool stack as infrastructure — a tiered failover chain, kept warm, because *the backup you never test isn't a backup*. Exercise is a 24-hour detox run explicitly as a failover drill, where the useful finding is **where** the dependency actually bites.
- [x] **Discernment** (`lab-discernment.html`) — product/process/performance, why process is hardest, and the eight signals. The load-bearing connection: **product vs. process discernment is the platform's own "score process separately from outcome" principle pointed at the model instead of the learner.** Every Case here already runs that split on the human; nobody had thought to run it on the AI's answer. Also names domain expertise as the prerequisite — without it a confident wrong answer and a confident right one are indistinguishable, which is the whole reason this module can't stand alone.
- [x] **Diligence** (`lab-diligence-agentic-boundary.html`) — creation/transparency/deployment diligence, then the piece with no equivalent anywhere else on the platform: **the agentic boundary.** Augmentation touches your context, Agency touches the system, and *a wrong firewall rule pushed by an agent doesn't get walked back with "well, the AI suggested it."* Disclosure follows blast radius; the personal-account boundary (read-only on personal tooling, write/push/execute needs the org to fund and own the accountability) is stated plainly. Links forward to Phase 6 as the safe place to build these habits.
- [x] **Case: the narrativized ticket** (`case-narrativized-ticket.html`, island `case-narrativized-ticket`) — an assistant drafts a ticket update asserting investigation and verification that never happened. The strongest distractor is *asking the assistant whether its own summary is accurate*, which is structurally incapable of catching it. Feedback is deliberately fair to the model: pattern completion, not deceit — a competent ticket update has a shape, and it filled the shape.
- [x] **Case: correct advice, wrong sequence** (`case-stack-sync.html`, island `case-stack-sync`) — starts mid-investigation with the pull-prompt already having narrowed correctly. The assistant's next suggestion is accurate and wrongly ordered, and the check it sends you to **cannot distinguish your hypotheses**: clean interface counters on a stack with a sync problem look identical to clean counters on a healthy one. Correct-and-useless as its own category. The good move is overriding advice that isn't wrong — the harder version of the skill.
- [x] **Drill: Automation / Augmentation / Agency** (`drill-interaction-mode.html`, island `drill-interaction-mode`) — one test settles it: *did the state of a system change without a human executing the change?* Both wrong answers get their own rebuttal, and the Automation distractor is the interesting one (a script encodes decisions you made in advance; here the assistant made the interpretive call and left no artifact).
- [x] Module index restructured from a flat list into the four competencies plus an "underlying literacies" group for the packet-capture and console material, with a compact framework reference at the top. Anthropic's framework credited once as the source of the four Ds and three modes; everything else is that framework applied to infrastructure work, which is not where its examples usually live.
- [x] Added a second `"what changed"` variant to `concepts/diagnostic-methodology.html` — not the existing "no proximate change at all" caveat, but **a change that happened and was never reported, because the person who made it didn't classify it as one.** Ask what was *done*, not what changed. Sourced from the stack Case's real root cause.
### Phase 5c — corrections from Tasha's own practice

Delivered against the 5b pages after reading them. All of these are her corrections to content originally drawn from her own older notes, so where the two disagree, **this section wins** — the notes describe what she thought at the time of the course, these describe what nine years actually looks like. She's flagged that the Notion source section likely needs rewriting or replacing to match.

- [x] **"Delegation is the leg people skip" was wrong, and is now the opposite claim.** It isn't skipped — it's decided in about the time it takes to pick left or right at a familiar junction. Fast and largely subconscious is not the same as absent: a tool got picked, a scope got picked, an acceptance bar got set. The lab now says the decision *ran*, it just didn't announce itself, and the skill is being able to surface and check it when the stakes justify slowing down.
- [x] **Problem Awareness rebuilt around the scientific method**, per her structure, because in IT the full problem usually *isn't* understood — that's why a tech was called. Six steps, each mapped to where an assistant does and doesn't fit: (1) *ask a question* — free in ITOps, the end user asks it as a complaint, but a complaint is a symptom and not necessarily the problem; (2) *research* — where AI does most of its real ITOps work and where push/pull/discovery prompts live; (3) *form a hypothesis* — a model's list of plausible causes **is** the hypothesis set, and a good session picks a favourite, says why, and says how to prove it; (4) *run an experiment* — "how would I check that" is the experiment; (5) *analyze data*; (6) *conclusion*. Plus the loop-not-line note and the named failure: **treating step 3 as the starting line**, arriving with a hypothesis and using the assistant to build a case for it rather than test it.
- [x] **The discovery prompt named as a third shape** (her term; she noted she didn't have a name for it). Push = enough context, ask directly. Pull = narrow toward a cause. Discovery = you don't yet know what evidence *exists*, so have the model walk you through what could be looked at — which logs, which tests, what to ask the client. The distinction that makes it worth naming: **pull narrows, discovery widens.** Using pull when you needed discovery is how you narrow confidently inside a space that never contained the answer. Also her diagnostic signal, now in both labs: **a push prompt that gets no traction is telling you about your prompt, not the model** — it's underfed, and switching modes fixes it where re-wording doesn't.
- [x] **Platform Awareness reframed as "which one, and at what tier."** For anyone running multiple models the real decision is model choice, and it mostly resolves on familiarity and proven consistency — treated here as a legitimate criterion rather than laziness, because knowing how a given model fails is what lets you catch a bad answer fast. What overrides it, consciously: the shape and size of the data (a three-thousand-row export is enough on its own to push up a tier), thread longevity, expected turn count, recency needs.
- [x] **"You do not need the largest model available for most of this."** If you're deliberate — real description, evidence fed back, hypotheses tested — a mid-range daily driver covers the overwhelming majority of ITOps work; discipline substitutes for horsepower further than people expect. Escalate for volume or genuinely hard reasoning, not by reflex. Plus two practical notes: reasoning/thinking-depth toggles are part of the decision surface rather than a setting to leave alone, and **the tier you want isn't always exposed in the interface you're in** — the same provider can surface different models in different modes of its own product.
- [x] **Where the volume actually is, stated on the index and in the Diligence lab:** ITOps is ~90–95% Augmentation — a tech brings a problem and the session is some mix of research, discovery, remediation and documentation (ticket, wiki, or both). Automation and Agency are **the minority by volume and the majority of the risk**, which is the reason the mode distinction is worth being pedantic about at all.
- [x] `concepts/diagnostic-methodology.html` now points at the six-step mapping as a spine — that page is a menu of techniques, and the scientific-method loop is something to hang them on, useful independent of the AI angle.
- [x] **Push prompts: declare your blind spots.** If you know there are holes in what you're handing over — you don't have that log, you can't reach that box, you don't know how to check that piece — say so in the prompt. An unflagged gap gets filled with an assumption you never see; a flagged one usually gets addressed, and naming it is often what turns a push prompt into a partial discovery request without starting over. Folded into the scope/capability habit too, since blind spots and access limits are the same species of declaration.
- [x] **The comprehension precondition, added to Discernment — and it's the most important single addition to the module.** Everything in that Lab silently assumed the tech understood the output. When a model pitches above their level (constantly, since it has no reliable way to gauge that level), *none of the three types actually run* — the tech is pattern-matching on confidence and picking the answer they already wanted. Three named failure shapes: **paraphrase drift** (restating badly and landing on the pre-chosen option — the specimen is confidently emptying `C:\Windows\Installer` to reclaim space and breaking every future repair/patch/uninstall), **scope creep in the artifact** (a script that does more than was asked; usually harmless, and if you can't read it you can't tell which case you're in), and **unexplainable outcomes** ("the AI told me to").
- [x] The nuance on that third one, which is Tasha's own and is the part nobody writes down: **it splits into two failures that look identical from outside.** One is not having understood it. The other is having understood it fine and being unable to *verbalize* it end to end — which produces the mirror-image mistake of explaining at your own level rather than the listener's, then fielding fifty questions you created. Same symptom, opposite causes, and the second is far more common among people who are good at this than anyone admits.
- [x] **The remedy, as a standing habit rather than a check:** ask the model for the *why* or *how* every time, not only when suspicious. Three payoffs — discernment becomes possible at all, the change becomes explainable afterwards, and technical knowledge compounds, since this is the cheapest available technical education and it arrives attached to a real system at the moment you have context for it. Four reflex phrasings given, the load-bearing one being *"explain it as though I'll have to explain it to the next tech"* — that forces a **transmissible** explanation rather than merely a correct one, which is the only one of the four that fixes both halves of the third failure.
- [x] **The fallback ladder for when "ask why" doesn't land** — Tasha's own practice, and she notes she's done this more than a few times. Two legitimate reasons you can still be lost after asking: it's above where you are, or **you have the knowledge and not the bandwidth** (end of a long shift, three tickets deep). The second is deliberately treated as equal to the first rather than a lesser version, because a tired tech and an inexperienced one make identical mistakes with a script neither of them read.
- [x] **Cross-checking with a completely unrelated model is substitution** — the named technique from the methodology page with the *model* as the swapped variable. The precision that makes it worth writing down: re-asking the same model or a sibling in the same family isn't swapping the variable at all, it's re-running the same test and treating the repeat as confirmation. Correlated errors stay correlated. Explicitly framed as the same error as reading the certificate from your own desk in the near-miss Case — right instinct, wrong vantage point. Also phrase the ask as "what does this do and what would it affect," not "is this right," which is an invitation to agree.
- [x] **Length as the trigger, and the one check still available when comprehension isn't.** A script noticeably longer than the job you described is the detectable signal for the scope-creep failure — and length is judgeable on sight without reading a line. Added to the signals list too.
- [x] **The honest limit on a second opinion:** it can catch a factual error, a dangerous flag, or an artifact doing more than its description claims. It cannot tell you whether the thing fits *your* environment, because neither model knows your topology, change windows, or what's unusual about that box. Two models agreeing is a better-informed hypothesis, not verification against the live system.
- [x] **Run it somewhere isolated regardless** — offline box, lab VM, something reimageable without a conversation. Justified on asymmetry rather than suspicion: twenty wasted minutes against an outage plus an explanation you already know you can't give. The ladder stated as a whole: **understand it if you can; cross-check when you can't; contain it regardless** — each rung leaning less on comprehension and more on containment, which is the right trade when comprehension is the missing thing.
- [x] Payoff added back in Delegation: the multi-model stack **earns its keep twice** — availability is the obvious reason for a second option, and an unrelated model as a diagnostic instrument is the non-obvious one. Which is a concrete argument for keeping the tiers on different providers rather than different sizes of the same one.
