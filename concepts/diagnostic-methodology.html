Named Diagnostic Methodology

Not protocol knowledge — these are the moves that decide what you check next, regardless of which protocol you're in. Every Case on this platform is really testing which of these you reach for.

Half-splitting / binary search

Pick a midpoint in your hypothesis space, test it, discard whichever half it rules out. Originates in electronics/radar fault isolation — voltage and continuity checks — and transfers cleanly to computer systems with different test points: a command output or a log line instead of a multimeter reading.

Substitution

Swap in a variable known to be good — a known-good account, a second machine, a different DC or resolver — and see whether the failure follows the swap or stays put. Arguably the most-used move in practice: it shows up independently across nearly every real field playbook, from "test with an account that's signed into other systems today" to "try a second machine on the same DC."

Top-down vs. bottom-up traversal

Work from the application layer down, or the physical layer up — whichever is cheaper to check first given what you already know about the symptom.

"What changed"

Establish the last known-good state before touching anything; most real root causes are a delta, not a mystery. Caveat: some failures — stale replication, a certificate hitting its expiry date, a service race condition — have no proximate human "change" at all. Treat this as the default first question, not a guaranteed answer.

Symptom vs. root cause

A reboot or a reimage can "fix" something without anyone ever learning why. That's not always wrong under time pressure, but it means the same failure can — and often does — recur later, with nobody any closer to the actual cause the second time either.

Behavioral / temporal observation

When a tool gives no explicit signal at all — no alert, no log line, nothing to half-split against — the only remaining move is watching state change over time and inferring the fault from the pattern of that change. There's nothing to read here, only something to watch — a genuinely different move from everything else on this list, and the one most easily forgotten because it doesn't feel like "checking" anything.

Classify before you diagnose

Sort an error into a category — authentication vs. authorization vs. account-state; signal vs. silence vs. bad-value — before acting on it. This is deliberately its own exercise type (Classification Drills) on this platform, separate from a full Case: the failure mode it targets is pattern-matching on a keyword and jumping to a remembered fix instead of actually parsing what's printed on the screen.
