Back to the Monitoring trailhead

Monitoring is where Signal vs. Silence shows up in its purest form — nearly every monitoring protocol has its own three-bucket version of the same taxonomy, and confusing the buckets wastes real investigation time.

SNMP's three buckets

  1. No response — error -2003 or a plain timeout. Ambiguous: wrong credentials, wrong version, a blocked port, the service down or bound to localhost only, a restrictive ACL. Any of these look identical from here.
  2. "I don't have that" — No Such Object / No Such Instance. Usually a MIB/OID mismatch, often from a firmware upgrade that silently renumbered an OID. The device answered fine; it just doesn't have anything at that specific address anymore.
  3. A value that's genuinely bad — the only bucket where "go fix the underlying thing" is actually correct.

Ping's nuances are sharper than they look

  • "Request timed out" — genuinely ambiguous, five-plus possible causes.
  • "Destination host unreachable" — an explicit reply from an intermediate router, not the target. Points at routing, not the destination itself.
  • "Destination port unreachable" on a UDP probe — counter-intuitively proves the host is alive. Only a live host generates that specific ICMP reply.
  • "Could not find host" — never even left the resolver stage. The network layer was never touched.
Four different strings that all read as "ping failed" to someone skimming quickly — and each one points at a completely different layer to check next.

The same taxonomy, other protocols

HTTP monitoring maps cleanly: connection refused / DNS failure (no signal) vs. a clean 404 or a TLS handshake with the wrong cert (explicit rejection) vs. a slow-but-200 or a 500 (bad value). Database and log-based monitoring generalize the same way — the buckets are the pattern, not the protocol.
