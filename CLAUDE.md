# CLAUDE.md — Beyond the Diagram (repo root)

## What this repo is

An IT fundamentals & troubleshooting learning platform — teaches protocol/system mechanism *and* diagnostic methodology, and uses a troubleshooting-game layer (Cases) to test the second using the first. Sibling in spirit to `webApps/portfolio/` (same author, same vault), but a serious standalone educational tool rather than a toy/game portfolio piece — don't carry over portfolio conventions (easter-egg protocol, whimsical tone) here without deliberately deciding to.

## Source of truth

**`it-troubleshooting-platform-concept.md` is canonical.** It's the full design doc — origin/vision, difficulty tiering, the three content types (Labs/Cases/Classification Drills), cross-cutting concepts (Signal vs. Silence, Eventual Consistency, Fail-Open vs. Fail-Closed, Trust-Boundary Flattening), named diagnostic methodology, the AI-fluency module, home-lab track, domain module content, and its own "Open Design Questions" section (scope and version-pinning strategy are still undecided; tech stack is resolved — see Structure section below and ROADMAP.md Phase 1). Don't duplicate its content into other docs; reference it instead. If code/implementation ever disagrees with it, flag the discrepancy rather than silently reconciling.

`ROADMAP.md` translates that concept doc into a phased backlog. Update the roadmap as phases complete or priorities shift; the concept doc itself should stay a stable reference, not a running task list.

## Structure — resolved: static-first with React islands (Phase 1)

Tech stack question is resolved. Not "fully static" or "fully React" — split by whether a piece of content actually holds state:

- **Static, no JS**: everything without a state machine — Labs prose, cross-cutting concept pages, domain module content, nav, landing. Includes the AI Fluency module: it's a paired weak-prompt/strong-pull-prompt example plus "now run both yourself against your own AI tool," never a live model call, so it never needed a backend or API key in the first place. Authored as plain HTML/CSS for now; revisit a static-site generator only once page count makes hand-authoring genuinely painful.
- **React, one isolated component per content type**: only where there's real state to hold — Cases (investigation path + score, process scored separately from outcome), Classification Drills (attempt + feedback), the placement quiz (answers → per-module tier, behavioral not self-reported). Each is a separate Vite entry point mounted into a `<div id="...">` on an otherwise-static page — not one SPA with a router owning the whole site. `app/`'s job is to build these bundles, not to be the app.
- **State persistence**: localStorage only, scoped to the browser. No accounts, no backend, resets on a cleared cache or a new device — that's the deliberate tradeoff for this stage, not an oversight. A shared, small localStorage wrapper module belongs in `app/src/`, imported by whichever island needs it, rather than each island rolling its own key scheme.

The stock Vite+React+TS template (counter demo, logos, docs/social links) has been stripped. `app/` now builds thirty real islands, each following the same pattern — a component + `main.tsx` mount entry, colocated CSS inlined via `import styles from './Component.css?raw'` + `<style>{styles}</style>` (never a normal CSS import — see the CSS-dedup bug note below), registered as an entry in `vite.config.ts`, previewable via the dev-only sandbox at `app/index.html`. Two of them are Phase 1 proof islands that graduated into real module content rather than being duplicated — `case-trust-relationship` (AD/GPO's Case) and `drill-401-403` (Authn/Authz's Drill) — worth checking for that pattern before writing new content for a domain. Per-module content:

- `case-dhcp-apipa` / `drill-dhcp-1059` — **DHCP** (Phase 2)
- `case-dns-split-horizon` / `drill-dns-nxdomain` — **DNS**, linking to Signal vs. Silence
- `case-spf-lookup-limit` / `drill-spf-softfail` — **Email Authentication**, the Drill linking to Fail-Open vs. Fail-Closed
- `drill-domain-not-available` — **AD/GPO**'s new Drill (Case is the reused `case-trust-relationship`)
- `case-entra-group-sync` / `drill-entra-pending` — **Cloud Identity**, linking to Eventual Consistency
- `case-snmp-oid-mismatch` / `drill-ping-port-unreachable` — **Monitoring**, linking to Signal vs. Silence
- `case-radius-reason-code` — **Authn/Authz**'s new Case (Drill is the reused `drill-401-403`), linking to Trust-Boundary Flattening
- `case-ldap-appliance-dead` / `drill-ldap-invalid-credentials` — **Remote Access/VPN**, the Drill linking to Trust-Boundary Flattening
- `case-vlan-loop` / `drill-switch-no-alerts` — **Abstracted Networking Gear**, linking to Signal vs. Silence and behavioral/temporal observation
- `case-ai-near-miss` / `drill-unpaired-question` / `drill-console-cors` — **AI Fluency** (Phase 5), the Case being the concept doc's anti-easter-egging principle made concrete (a confident, plausible, wrong AI answer quoted up front), the Drills linking to classify-before-you-diagnose and Signal vs. Silence
- `placement-quiz` (Networking Fundamentals, shared by DHCP+DNS) plus one `placement-quiz-<domain>` island per remaining module (`email-auth`, `ad-gpo`, `cloud-identity`, `monitoring`, `authn-authz`, `remote-access`, `prosumer-networking`, `ai-fluency`) — 9 quizzes total, every built module covered, each linked from that module's own `index.html`

All domain-module islands are structurally identical to the two Phase 1 proof islands — different content, same shape — confirming the islands pattern generalizes rather than being a one-off. **All nine domain modules from the concept doc are built (Phase 4), and per-module placement tiering is proven for real, not just in theory (Phase 3): took two different modules' quizzes with opposite-signal answers in the same session and confirmed each persisted its own tier independently rather than sharing one global result.** **The AI-fluency module (Phase 5) is built too** — same folder shape, but it's a meta-skill rather than a tenth domain, so it's labelled that way instead of getting an ordinal, and it carries three Labs instead of one because the concept doc names three distinct sub-skills under it (the pull-prompt, packet-capture baseline articulation, browser-console literacy). Nothing in it calls a model; the prompt comparisons are worked examples plus a "run both yourself" exercise, exactly as Phase 1 predicted.

See `app/README.md` for the exact steps to add another island. `src/lib/progress.ts` is the shared localStorage wrapper every stateful island uses — attempt logging (with an optional `meta` field for extras like process-vs-outcome), plus a separate per-module tier store for placement.

**Content pages live in a per-domain folder at the repo root** — `dhcp/`, `dns/`, `email-auth/`, `ad-gpo/`, `cloud-identity/`, `monitoring/`, `authn-authz/`, `remote-access/`, `prosumer-networking/`, and `ai-fluency/` are all one pattern: a module `index.html` linking to one page per content item, Labs as plain static HTML/CSS, Cases and Drills as a thin static page mounting the matching island. **`concepts/`** holds the cross-cutting reference material (Signal vs. Silence, Eventual Consistency, Fail-Open vs. Fail-Closed, Trust-Boundary Flattening, and the named diagnostic methodology) — every domain module links into it rather than re-explaining a pattern from scratch; retrofit older modules when a new one's content overlaps with a concept they already used implicitly. `it-troubleshooting-platform-concept.md` is the source for all of this — write new domain content from there, not from scratch.

**Deploy is resolved: GitHub Actions, not committed build output.** `.github/workflows/deploy.yml` builds `app/` on every push to `main`, then assembles the deployed site via an *exclude*-based `rsync` (skips `.git`, `.github`, `.claude`, `app/`, docs, `LICENSE`) rather than an explicit copy-list — a new top-level content folder ships automatically, it doesn't need the workflow edited. Learned this the hard way: the first version only copied `index.html`+`CNAME`+built islands, which would have silently 404'd on `assets/`, `dhcp/`, and `islands-demo.html` once deployed — caught by a local dry run before it ever shipped, not after. `islands-demo.html` at repo root is the proof/QA page: it references every built bundle directly (`/islands/<name>.js`) so it only works once actually deployed (or against a local static-file simulation of `_site/`), unlike `app/index.html` which is dev-only.

**A second real bug, same root cause (unhashed filenames), different asset type:** islands originally linked their CSS as a normal stylesheet (`import './Component.css'`), emitted to `islands/assets/<name>.css` with the hash deliberately dropped so hand-written pages could link a stable name. That works until two islands' CSS ends up byte-identical after an edit — which happened for real between the DHCP and DNS Drills once both got the same `.drill a` rule added — at which point Rollup silently dedupes them into one file and the other island's page 404s on its stylesheet. Fixed by having every island inline its CSS via `?raw` + `<style>` instead of a linked stylesheet, which sidesteps the whole asset-naming problem (no CSS asset is emitted at all) and means a consuming page only ever needs the one `<script>` tag. Caught by the same local dry-run practice as the deploy-workflow bug above — always verify new content against an actual assembled `_site/`, not just the dev sandbox, before pushing. **One manual step still needed:** GitHub Pages' source needs to be switched to "GitHub Actions" in the repo's own Settings → Pages before this workflow can actually publish anything.

## Case-sensitivity (deploy-time gotcha)

Same caveat as the portfolio repo: local dev is likely Windows (case-insensitive), GitHub Pages is Linux (case-sensitive). Verify on-disk casing matches link casing exactly before committing.
