Lab: the Entra ID / Intune propagation pipeline

"It's assigned, why doesn't the user have it" is one of the most common cloud-identity tickets, and it's genuinely ambiguous — the change has to clear several independently-owned stages before it's actually in effect anywhere. This is the same Eventual Consistency pattern as on-prem AD replication, just with cloud-specific names and timings.

The five stages

StageWhat happensTypical timing
Directory writeGroup owner adds the user, or an admin changes an attributeImmediate
Inter-node propagationEntra Connect delta sync (hybrid only)Default every 30 min
Membership re-evaluationDynamic group re-computes its member listNo published SLA
Policy deliveryIntune pushes the assignment via WNSUsually minutes — but only for admin-initiated changes
Client applicationDevice checks in and applies what's newDefault 8 hrs; Config Refresh tunable to 30 min, default 90 min (deliberately mirroring GPO)
Forcing a device sync only ever helps the last stage. If the hold-up is dynamic group re-evaluation — which has no published SLA at all — a forced sync just makes the device check in early against a directory state that hasn't caught up yet. It'll report back cleanly and show nothing new, which can look like "the sync didn't work" when really there was nothing yet for it to find.

Session-level caching is a separate, sixth thing

Even once every stage above has finished, a live session can still be running on stale authorization: a Primary Refresh Token (PRT) embeds group membership at the time it was issued, similar to how a Kerberos TGT embeds group SIDs at logon on-prem. A user might need to actually sign out and back in — not just wait — before a completed propagation shows up in their live session.
