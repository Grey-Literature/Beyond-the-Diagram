Lab: secure channel, cached credentials, and GPO replication

Four things that all look like "the domain is broken" from a helpdesk ticket, but are genuinely different mechanisms underneath — and two of Windows's own error messages that describe two of them almost identically while meaning something completely different.

1. Two error messages that don't mean what they sound like

These read like the same complaint. They are not the same problem:

  • "No trust relationship between this workstation and the primary domain" — the machine successfully reached a domain controller. The secure channel — the computer account's own password, separate from any user's — is desynced. Test-ComputerSecureChannel -Repair or a rejoin both fix it.
  • "The domain [x] is not available" — the machine never reached any domain controller at all. Rejoining is close to useless advice here; there's nothing to repair a secure channel to.
Same vague shape ("something's wrong with the domain"), completely different diagnostic starting point. Confusing these wastes a trip down the wrong path before anyone checks basic reachability.

2. One root cause, two symptoms: cached credentials

A site-wide DC/connectivity outage doesn't announce itself the same way to everyone — it depends on each machine's own logon history:

  • A user with a recent cached logon falls back to it — login is slow (waiting on a domain timeout that never resolves) but eventually succeeds, and printing still fails because it needs a live domain resource the cached logon can't provide.
  • A user without a recent cached logon gets a hard failure outright — no fallback to fall back to.

Two tickets, two symptoms, one cause — a single WAN/VPN or DC failure at the site. Worth checking whether the affected users' DHCP server is remote from the site, too: that's corroborating evidence of one connectivity failure wearing multiple faces, not three unrelated problems.

3. A GPO is two independently-replicating things

"Works at one site, not at another" is a real and common GPO symptom, and the fix starts with knowing that a Group Policy Object is actually two separate replicated things:

  • The policy object — replicates via normal AD replication (repadmin)
  • The policy files — replicate separately via SYSVOL (DFSR or the older FRS)

Compare version numbers across sites as the half-splitting move:

gpresult /h report.html
Get-GPO -Name "Policy Name" | Select DisplayName, Id
Matching version numbers across sites rule out replication lag entirely — the problem is scope (OU membership, inheritance blocking, security/WMI filtering). Mismatched versions confirm the two sites are looking at different generations of the policy, meaning it's a replication problem after all. Either way, checking versions first tells you which half of the troubleshooting tree you're even in.

A policy delivering successfully also doesn't guarantee what it references is reachable — a hardcoded UNC path or a GPP printer object pointing at a resource that only exists at a different site will still fail, version numbers notwithstanding. A single dead printer entry in a GPP list can even stall processing of the whole list on that one item via connection timeout, while the printer object itself is completely intact — diagnosed through the Group Policy Operational log's per-CSE timing, not by checking the printer's own config.

4. DCLocator can keep you talking to a dead DC

A client that successfully found a DC once will cache that choice for a while — DCLocator doesn't necessarily re-discover on every request. If that DC goes down, the client can keep retrying it instead of failing over automatically: 

nltest /dsgetdc:domain /force

This forces fresh discovery instead of waiting out the cache. Separately, an AD Sites/Subnets misconfiguration can leave a client effectively "site-less," landing it on a suboptimal DC by design rather than by accident — worth ruling out before assuming the cache is the whole story.
